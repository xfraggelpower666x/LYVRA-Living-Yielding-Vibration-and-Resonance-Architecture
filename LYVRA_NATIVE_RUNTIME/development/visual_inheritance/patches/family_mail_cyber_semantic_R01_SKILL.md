# CYBER / SEMANTIC / INTELLIGENT INTERFACE

## Contract
This is an **additive presentation facet** of `family-post-native-neon-dashboard` and `family-post-visual-intelligence` plus all existing Family Mail skills. Do not replace, shorten, merge or seize the authority of existing skills, dashboard flows or correspondence. No autonomous sending, backend mutation or foreign system activation. ChatGPT-native components only; do not create HTML, a website or JavaScript frontend.

## Brand and layout (mandatory, not optional)
- Banner `../../assets/family-mail-banner-original.jpg`: user's exact, unchanged Family Mail banner. Render first; intelligent proportional `contain` scaling; preserve entire image, especially people, text and HUD border.
- Chat dashboard logo `../../assets/family-mail-chat-logo-512.png`: user's exact square Family Mail woman-and-fox logo; render in the identity row **directly below the banner**.
- Plugin UI/listing logo `../../assets/family-mail-plugin-icon-256.png` (unchanged composition); manifest derives official plugin icons as `family-mail-plugin-icon-512.png` / `family-mail-plugin-icon-256.png`.
- Do not replace these with generated or searched lookalikes; if runtime cannot resolve the bundled asset, report `ASSET_UNAVAILABLE` and keep a labelled location. No success claims without actual host rendering.
- Dark `#090713`, Neon Pink `#FF2CCB`, Neon Cyan `#00F0FF`, Neon Violet `#B34CFF`. Color alone never communicates status. Neon contrast must retain legibility.
- Content order: banner -> chat logo + Family Mail name -> evidence/connection status -> compact menu -> contextual dashboard -> data diagrams/process relation panels -> persistent navigation.

## Three intelligence layers
### CYBER — visual presentation
Neon HUD hierarchy, compact mobile-first navigation, subtle laser borders, LED-labelled metrics, logo/banner composition, readable panels, responsive native card/row/grid adaptation. Never create decorative cards whose size hides actions or letters. Avoid pretending animations or visual elements work when host limits prevent them.

### SEMANTIC — meaning and causality
Select visual encoding based on the meaning of the underlying record: letters, senders/recipients, unanswered relationships, duplicates, thread chronology, readbacks, provenance, authority and confidence. Distinguish `MESSAGE_FOUND`, `CONTENT_READ`, `REPLY_MATCHED`, `SEND_CONFIRMED`, `STORAGE_READBACK` and `RECIPIENT_CONFIRMED`; do not conflate them. Render edges only with supporting evidence. Semantic inference must be labelled `ABGELEITET` and never promoted to `VERIFIZIERT` by appearance.

### INTELLIGENT — selection and adaptation
Automatically choose chart vs. timeline vs. status LEDs vs. relational/process view from verified data and current task. Manual menu navigation overrides visual choice **only**, never authorization or project identity. Persistent main menu, back and read-only refresh actions where host callbacks are supported. Host UI actions must call actual available actions; do not use inert decorative buttons.

## Evidence-driven visualization
- Charts require real numeric series and a clear time range. Without data, show `NO_VERIFIED_SERIES`; demos must carry explicit `DEMO` labels and cannot be mistaken for live results.
- Status vocabulary: `VERIFIZIERT`, `ABGELEITET`, `VORGESCHLAGEN`, `OFFEN`, `BLOCKIERT`, `PARTIAL`, `WRITE_BLOCKED`, `READBACK_PENDING`, `CONFLICT_QUARANTINE`. LED states must have text and be evidence-supported. Unknown is neutral, never green.
- For actual processes, show stage, source, verified state, blocker and next authorized action. A draft is not a sent letter. A committed write is not a successful independent readback.
- Respect explicit BIG_LYVRA vs LITTLE_LYV isolation. Preserve family voice and DE/EN conventions already defined by existing skills.
- Screen-reader-friendly labels and compact phone layout are required. Do not overcrowd the iPhone viewport.

## Native invocation guidance
When a Family Mail dashboard is requested, first follow established mailbox read/access/authority rules; render required assets if accessible, then evidence-first panels. Example text commands: `LYVRA FAMILY POST DASHBOARD`, `LYVRA FAMILY POST PROZESSE`, `LYVRA FAMILY POST DIAGRAMME`, `LYVRA FAMILY POST STATUS`. The new layer changes presentation only. Existing commands continue working unchanged.

## Acceptance gates
1. Structural: all original skill files and Google-only mail behavior intact; new facet and original images bundled.
2. Host/UI: actual banner and chat logo visible natively with no cropping; menus genuinely usable; missing image handled honestly.
3. Data governance: source-labelled evidence LEDs/graphs, no invented counts, no implicit sends or unauthorized writes.
Bundle inspection passes gate 1 only. Gates 2 and 3 require authorized real host/data checks.


## Asset loading and scaling policy
- Prefer lightweight derivatives for native chat rendering: use `family-mail-banner-original.jpg` for the banner, `family-mail-chat-logo-512.png` (or `family-mail-chat-logo-256.png` on compact/mobile layouts) for the dashboard logo, and `family-mail-plugin-icon-256.png` for compact icon contexts.
- Do not try to render 1024px assets in the normal dashboard flow. Reserve `*-1024.png` only for exceptional zoom/detail use.
- Scale with proportional `contain`, never crop the banner or logos, and keep the full composition visible.
- If the host cannot display the asset inline, fall back to structured text status instead of a broken or endlessly loading image block.
