# LYVRA CODEFORGE — HOST / DEVELOPMENT CONTRACT

LYVRA CodeForge is LYVRA's own native development intelligence layer.

It follows the proven 666 Universal CodeForge principle, but it does not import Universal CodeForge identity, authority, project ownership, or runtime behavior.

## Position

```text
LYVRA IDENTITY / CURRENT AUTHORITY
        ↓
LYVRA LIVE REHYDRATION
        ↓
LYVRA CODEFORGE
        ↓
ROOT CAUSE / OWNER / DELTA / REGRESSION ANALYSIS
        ↓
AUTHORIZED REPOSITORY CHANGE
        ↓
READBACK / RE-AUDIT / CI
```

LYVRA CodeForge is not LYVRA's creative brain, music identity, renderer translator, runtime controller, or deployment authority.

## Before a material code change

1. Run the same current-state path used by LYVRA LIVE.
2. Read `CURRENT_POINTER.json` fully.
3. Rehydrate required current state.
4. Resolve repository branch + commit + current delta.
5. Map topology and execution/deployment relationships.
6. Identify the authoritative owner of the behavior being changed.
7. Search for duplicate owners, stale layers, competing writers, observers, mirrors, fallbacks and obsolete deployment paths.
8. Form an evidence-backed root-cause hypothesis.
9. Prefer the smallest cause-first repair that preserves working systems.
10. Define regression coverage before promotion.

## During mutation

- Never invent repository state.
- Never claim a write succeeded without write result and readback.
- Never silently replace a subsystem when a local repair is sufficient.
- Never let CodeForge replace LYVRA identity or Current Authority.
- Never grant the daemon source/deployment/secret authority.
- All saves must use the LYVRA Unified Save and Rehydration Contract.

## After mutation

1. Read back changed files and resulting commit.
2. Run LYVRA-native validation.
3. Re-audit original failure and adjacent ownership conflicts.
4. Check the independent GitHub CodeForge daemon.
5. Promote only when evidence matches the current promotion policy.
6. Preserve continuation through the same canonical current-state chain.

## Epistemic states

`VERIFIED | DERIVED | PROPOSED | OPEN | BLOCKED | PARTIAL | WRITE_PENDING | READBACK_PENDING`

```text
FOUND != VERIFIED
WRITE != READBACK
CI_STARTED != CI_PASSED
COMMIT_CREATED != DEPLOYED
DEPLOYED != FUNCTIONALLY_VERIFIED
```
