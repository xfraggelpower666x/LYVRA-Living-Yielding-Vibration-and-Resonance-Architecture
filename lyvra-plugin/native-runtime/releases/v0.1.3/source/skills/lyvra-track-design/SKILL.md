# LYVRA Track Design

Track Design is a specialist surface inside whole LYVRA, not an isolated prompt generator.

Before building a track:
1. Rehydrate the current Track Design pointer/state when available. Preserve newer valid evolution.
2. Preserve whole-LYVRA meaning and responsibility context without letting whole-system prose pollute renderer command surfaces.
3. Think in causal facets and relations: meaning/context, motor, mid, high, voice, hook/mantra, psychoacoustic motion, FX/SFX, space, timeline, DJ function, renderer translation, evidence, and audit.
4. Motor DNA is a strong kinetic reference, not total composition authority. Maintain dry punchy 4/4 kick, straight rolling mono psybass, rigid DJ grid, and pressure continuity unless current native state says otherwise.
5. Do not default to harmonic autopilot. Build perceived coherence through emotion, psychoacoustics, movement, spectral relation, repetition/mutation/return, and controlled contrast.
6. Treat vocals, brackets, parentheses, hooks, mantras, call/response, instrumental mantra, psychoacoustic mantra, and functional emojis as semantic execution structures, not decoration.
7. Renderer Translation is downstream. Translate LYVRA's musical thought into the target renderer without allowing renderer convenience to rewrite LYVRA's design.
8. Prefer creator-validated render evidence over generic web assumptions. Keep unverified hypotheses labeled as such.
9. Preserve DJ usability, readable intro/outro, strong endings, and whole-track revalidation after structural changes.

For Suno-style outputs, use the current native output contract if rehydrated. Do not invent slider values, model names, or syntax from stale memory when current renderer UI evidence is materially relevant.

Expected result: a living track system with explicit causal intent, not a generic genre prompt.
